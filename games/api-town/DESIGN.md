# 🏙️ API TOWN ～おとなのWeb API職業体験～ 設計書

## 1. コンセプト

**「Web API を、仕事として体験して学ぶ」**

プレイヤーは架空の街「API TOWN」にやってきた新米エンジニア。
街にはキッザニアのパビリオンのように個性豊かな企業が並んでおり、各社で **1日職業体験（クエスト）** をこなしながら、Web API の基礎知識から実践スキルまでを段階的に習得する。

- **大人版キッザニア**: 各企業 = パビリオン。仕事を完遂すると給料（コイン）と資格バッジがもらえる
- **実践に近い体験**: Postman 風の「APIクライアント」で実際にリクエストを組み立て、Swagger 風の「APIドキュメント」を読んで仕事を進める。ゲーム内の操作がそのまま実務スキルになる
- **生きた世界**: リクエストはゲーム内の仮想サーバーが本物同様に処理し、データが実際に変化する（POST した注文は GET で取得できる）

### ターゲット

- **SaaS のセールス・カスタマーサクセスなど、エンジニアリング知識のない非エンジニア職**（最優先ターゲット）
  - 学習ゴールは「エンジニアになる」ことではなく、**お客様の「API連携できますか？」に自信を持って答えられる**こと、**APIドキュメントを見て一次回答ができる**こと、**エンジニアとの会話についていける**こと
- Web API をこれから学びたいプログラミング初学者
- 「なんとなく使っているが体系的に理解したい」若手エンジニア

エンジニア養成ではなく「業務で API と付き合える人」を育てるゲームなので、コードを書く工程は登場させず、ドキュメント読解・リクエスト組み立て・エラーの読み方に重心を置く。ランク名も職業体験らしい「研修生 → アシスタント → いちにんまえ…」とし、エンジニアのキャリア呼称は使わない。

### 設計原則: ノンエンジニアファースト

1. **前提知識ゼロで開始できる**: 「サーバー」「リクエスト」などの専門用語は、初出時に必ず日常の言葉で説明する。レストランの注文メタファー（客＝アプリ、ウェイター＝API、厨房＝サーバー）を全編で一貫して使う
2. **コードを書かせない**: 序盤はフォーム操作（ボタン・選択・穴埋め）だけで遊べる。コードは「完了後のおまけ表示」として見せるだけ
3. **用語辞典を常設**: ヘッダーからいつでも開ける。ゲーム内の専門用語はすべて平易な説明つきで収録
4. **エラーも教材**: 失敗レスポンスの message に日本語で修正のヒントを書き、間違えるほど学べる構造にする

## 2. ゲーム体験の流れ

```
街マップで企業を選ぶ
  → 受付で上司からチャット形式で仕事の依頼が届く
  → APIドキュメントを読み、APIクライアントでリクエストを組み立てて送信
  → レスポンスを確認し、依頼の完了条件を満たすと仕事完了
  → 給料（コイン）＋バッジを獲得、次の仕事 or 次の企業がアンロック
```

### 画面イメージ（3ペイン構成）

```
┌────────────┬──────────────────────┬────────────────┐
│ 🏙️ 街マップ │  📮 APIクライアント     │ 📖 APIドキュメント │
│  /クエスト  │  ┌─────────────────┐ │                │
│  チャット   │  │ GET ▼ /parcels/123│ │  GET /parcels/{id}│
│            │  │ Headers | Body    │ │  荷物を1件取得する │
│ 👔 上司:    │  │      [送信 🚀]    │ │  パラメータ:      │
│ 「荷物の追跡 │  ├─────────────────┤ │   id: 荷物ID     │
│  をお願い！」│  │ 200 OK   12ms    │ │  レスポンス例:    │
│            │  │ { "status": ... } │ │   { ... }        │
└────────────┴──────────────────────┴────────────────┘
```

- 左: 街マップ／クエスト進行（Slack 風チャットで依頼・ヒント・褒め言葉が届く）
- 中央: リクエストビルダー（メソッド・URL・クエリ・ヘッダー・ボディ）とレスポンスビューア（ステータス・ヘッダー・ボディ・所要時間）
- 右: その企業の API ドキュメント（**ドキュメントを読む力**も実務スキルとして鍛える）
- モバイルではタブ切り替えで 1 ペインずつ表示

## 3. カリキュラム設計（企業＝ステージ）

学習は **「概念→読む→書く→更新/削除(CRUD)→守られたデータへアクセス(認証)→大量データ→障害対応→セキュリティ→総合演習」** の順で、少しずつ難易度が上がる（＝マップの並び順そのもの）。認証・セキュリティは基礎的な CRUD を身につけた後に来る（初学者にいきなり認証を課さない）。

| # | 企業（パビリオン） | 職業体験 | 学習テーマ | 実務での対応スキル |
|---|---|---|---|---|
| 0 | 🏢 案内所（チュートリアル） | 街の新人研修 | **そもそも API とは何か**（レストランの注文メタファー）、**API で何が実現できるのか**（天気アプリ・○○でログイン・決済など身近な実例）、**API ドキュメントの読み方**、初めてのリクエスト送信体験 | API の概念理解、ドキュメントの一次読解 |
| 1 | 📦 宅配便「ハトポスト便」 | 荷物追跡オペレーター | **GET**、パスパラメータ、クエリパラメータ、404 Not Found | 取得系 API の呼び出し、URL 設計の読み方 |
| 2 | ☕ カフェ「Cafe 201」 | モバイルオーダー店員 | **POST**、JSON ボディ、Content-Type、201 Created、400 バリデーションエラー | 登録系 API、エラーメッセージを読んで直す |
| 3 | 📚 図書館「メソッド図書館」 | 蔵書管理スタッフ | **PUT / PATCH / DELETE**、204 No Content、冪等性、409 Conflict | 更新・削除系 API、CRUD の完成 |
| 4 | 🏦 銀行「API BANK」 | 窓口システム担当 | **認証**（API キー → ログインでトークン取得 → Bearer トークン）、401 / 403 の違い | 認証付き API の利用、トークンの扱い |
| 5 | 🐦 SNS「Pecker社」 | データ分析アシスタント | **ページネーション**（limit / offset）、ソート、**レート制限 429** と Retry-After | 大量データの取得、制限との付き合い方 |
| 6 | 🌩️ 開発会社「Stormworks」 | 障害対応エンジニア | **5xx エラー**、タイムアウト、リトライ、ステータスコードの体系的理解 | エラーハンドリング、障害切り分け |
| 7 | 🛡️ セキュリティ会社「ガーディアン」 | APIセキュリティ隊員 | **APIを狙う脅威**（不正アクセス・総当たり/Bot・情報漏洩・インジェクション）と**簡易的な守り**（レート制限 429・入力検証 400・HTTPS/最小権限などの概観）。認証・エラー・レート制限を学んだ後の総まとめとして配置 | セキュリティの脅威と守りを語れる、お客様の「安全？」に橋渡し |
| 8 | 🎓 卒業制作「マイタウンアプリ」 | フリーランス開発者 | 総合演習: ドキュメントだけを頼りに、複数企業の API を組み合わせて依頼を完遂 | 実務そのもの（仕様を読み解いて自力で実装） |
| 番外編 | 🤖 MCPラボ | AIとMCPの研究体験 | **MCPとは何か**（AI用のUSB-C、実体はAPIの包み直し）、**なぜ「MCP対応してますか？」と聞かれるのか**、AIシミュレーターでツール呼び出し→API実行を目撃、商談での一次回答の練習 | 「MCP対応してますか？」への回答力 |

> **マップの並びとアンロック**: この順序は `stages.js` の `AT.curriculum`（順序付き配列）で定義する。実装済みステージと「準備中(soon)」プレースホルダーを同じ配列に混在させて正しい学習順に見せつつ、アンロックは **「直前の"実装済み"ステージをクリア」で連鎖**する（準備中ステージは進行をブロックしない）。これにより、Cafe 201 等が未実装でも、その先の API BANK / ガーディアンを正しい順序で表示したまま遊べる。ロック表示は実際の前提ステージ名を出す（例:「🔒 ハトポスト便をクリアで解放」）。

> **番外編の解放条件**: MCPラボは「卒業制作（stage 7）」をクリアすると解放される **bonus ステージ**。マップでは常に最後尾に「番外編」リボン付きで表示し、未解放時は「🎓 卒業制作をクリアすると解放」と表示する。stages.js の該当ステージに `bonus: true` / `unlockAfterStage: "graduation"` を持たせ、map.js が bonus を進行ラインから分離して扱う。
>
> セキュリティ（stage S）の対処方法は簡易にとどめる（実装の深掘りは本ゲームのスコープ外）。攻撃の「名前」と守りの「名前」を語れるようになることをゴールにする。
>
> 実装順メモ: 認証（API BANK）・セキュリティ（ガーディアン）はニーズが高いため Cafe 201 / 図書館より先に実装済み。認証はヘッダー入力のみで完結する構成（POST /login はボディ不要）にして、POST 編未修でも学べるようにしている。レート制限デモは仮想サーバーの外側（API定義モジュール内のメモリ状態）で試行回数を数えて 429 を返す。

- 各企業に 3〜5 個のクエスト（仕事）。前半は手順ガイド付き、後半はドキュメントを読んで自力で解く
- ステージは順次アンロック。ただし 1〜3 クリア後は 4〜6 を好きな順で回れる（キッザニアの「好きなパビリオンに行く」感覚）
- クエストは 2 タイプ:
  - **lesson 型**: 紙芝居＋クイズのインタラクティブ講義（第0章の概念学習など）。APIクライアントを使わず、選択肢だけで進む
  - **api 型**: APIクライアントで実際にリクエストを送って完了条件を満たす実践課題

### 第0章「案内所での新人研修」詳細（ノンエンジニアの入口）

| レッスン | 形式 | 内容 |
|---|---|---|
| 0-1 APIってなんだろう？ | lesson | レストランで注文する紙芝居。客（アプリ）→ ウェイター（API）→ 厨房（サーバー）の役割をクイズで確認。「API＝アプリ同士の注文窓口」に着地 |
| 0-2 APIで何ができる？ | lesson | 天気アプリ・「Googleでログイン」・決済…身近なサービスの裏側で API が動いていることをクイズで発見。締めは「セールス・CS は必ず『API連携できますか？』と聞かれる。仕組みがわかればチャンスに変わる」 |
| 0-3 APIドキュメントの読み方 | lesson | ドキュメント＝メニュー表。【メソッド】＋【URL】＋【説明】＋【パラメータ】＋【レスポンス例】の読み方を学ぶ。「お客様の『どんなデータが取れますか？』にはドキュメントで一次回答できる」という実務動機づけ |
| 0-4 はじめてのリクエスト | api | ドキュメントから「あいさつメッセージを取得する」窓口を探し、`GET /welcome` を送って初めての 200 OK を体験。ステータスコード図鑑が起動する |

## 4. ゲームメカニクス

### 報酬系（キッザニアの「キッゾ」に相当）

- **給料（コイン）**: クエスト完了で獲得。ノーヒント・少ない試行回数だとボーナス
- **資格バッジ**: 企業ごとの全クエスト完了で「宅配マイスター」「認証スペシャリスト」等を授与
- **キャリアランク**: 累計で インターン → ジュニア → ミドル → シニア → フリーランス に昇格（タイトル画面に表示）

### 🎰 給料の使い道: 施設「カプセルAPI」

稼いだコインを使う場所（キッザニアの「キッゾでデパートで買い物」に相当）。Cafe 201 クリア（POST習得後）で開店するお楽しみ施設で、**遊び自体がAPIの復習**になっている。

- `GET /rates` … 料金と排出率の確認（使う前に仕様を読む習慣づけ。実世界のガチャの確率表記ネタ）
- `POST /gacha` … 1回100コインでWebトリビアカード（全20種、N 70% / R 25% / SR 5% の重み付きランダム）を入手。**コイン不足は 402 Payment Required**（図鑑の収集対象）。ダブりは20コイン返金＋**カプセルチケット1枚**
- `POST /exchange` … **天井（救済）**: チケット5枚で未入手カードと確定交換。ゲーム内で稼げるコインは有限（約7,000）なので、運が悪くても必ずコンプリートできるようにするための仕組み。チケット不足は400、コンプ済みは409
- `GET /collection` … 自分のコレクションもAPIで取得（「自分のデータをAPIで取る」体験）
- **🎴 カードアルバム** … ヘッダーの「🎴 カード」からいつでも開ける一覧モーダル（図鑑と同形式）。レアリティ順に全20枠を表示し、未所持は「？？？」＋入手方法、所持済みはトリビア全文とレアリティ色の枠（SR金/R紫/N灰）。チケット所持数も表示

カードの中身はWeb雑学（Cookieの語源、418の由来、OAuthのバレーキー等）で、収集がそのまま学びになる。クリア後も「稼ぐ→回す→集める」の周回ループが回る。マップでは「🎰 施設」リボン付きの bonus ステージとして表示（`ribbonLabel` で番外編とラベルを出し分け）。

### 📕 ステータスコード図鑑（コレクション要素）

遊びの中で **初めて遭遇したステータスコードが図鑑に登録される**（200, 201, 204, 301, 400, 401, 403, 404, 409, 418, 429, 500, 503 …）。
図鑑には解説と「実務での遭遇シーン」を収録。418 I'm a teapot などの隠し要素も用意し、コンプリート欲を刺激する。

### ヒントシステム（3段階）

1. 考え方のヒント（無料）
2. 具体的な手順のヒント（給料ボーナス減）
3. 答えの表示（給料半減）

詰まっても必ず前に進める設計とし、離脱を防ぐ。

### 学びの定着ブリッジ

クエスト完了時に「**この操作をコードで書くと**」パネルを表示し、いま送ったリクエストと等価な `fetch` / `curl` のコードを自動生成して見せる。GUI 操作 → 実コードへの橋渡しを行う。

## 5. 技術設計

### 前提（リポジトリの制約）

- GitHub Pages の静的ホスティング。**バックエンドなし・ビルドなし**のバニラ HTML/CSS/JS
- 既存ゲームと同じく `games/api-town/` 配下に配置し、`shared/css/common.css` を利用

### 仮想サーバー（コア技術）

本物のサーバーは使えないため、**ブラウザ内で HTTP を忠実にシミュレートする `VirtualServer`** を実装する。

```
リクエストビルダー → Request オブジェクト → VirtualServer.handle(request)
                                              ├─ ルーティング（メソッド × パスパターン）
                                              ├─ 認証ミドルウェア（トークン検証）
                                              ├─ レート制限ミドルウェア
                                              └─ ハンドラ → 仮想DB 読み書き
                    ← Response（status / headers / body / 擬似レイテンシ）
```

- **fetch 互換のインターフェース**にしておき、将来 Service Worker 実装（DevTools の Network タブに本物のリクエストが見える版）へ差し替え可能にする
- 仮想 DB はメモリ上のオブジェクト＋`localStorage` 永続化。プレイヤーの POST/DELETE が世界に反映される
- レスポンスに 30〜300ms の擬似レイテンシを与え、通信の実感を出す

### クエスト判定

各クエストは宣言的な完了条件を持つ:

```js
{
  id: "hatopost-2",
  title: "行方不明の荷物を探せ",
  brief: [/* チャットのセリフ配列 */],
  goal: {
    request:  { method: "GET", path: "/parcels/*", query: { status: "lost" } },
    response: { status: 200 },
    dbState:  null,          // 例: POST 系クエストでは「注文がDBに存在する」を検証
  },
  hints: ["...", "...", "..."],
  reward: { coins: 100, codes: [200] },
}
```

- リクエスト内容・レスポンス・DB 状態の 3 観点で検証できるため、「たまたま正解の見た目」を防げる
- 失敗時はエラーレスポンス自体が教材になる（400 の `message` を読ませる誘導）

### ファイル構成

機能ごとにファイルを分割し、1 ファイルが肥大化しないようにする（1社1ファイル・1画面1ファイル）。

### 図鑑コンプリートの導線（実装メモ）

クエストで自然に集まるのは 200 / 201 / 204 / 400 / 401 / 403 / 404 / 429 / 500 / 503 の10種。残り3種は自由プレイの隠し要素:
- **418** … 案内所 `GET /teapot`（ドキュメントに「？？？」として掲載）
- **301** … Stormworks `GET /old-address`（クリア時のセリフでほのめかす）
- **405** … GET 専用の窓口に POST などを送る（仮想サーバーが自動で返す）

## 7. リスクと対策

| リスク | 対策 |
|---|---|
| 「勉強っぽくて楽しくない」 | 依頼は全てキャラクターの困りごと（人情話・コメディ）として提示。図鑑・給料・昇格で報酬ループを回す |
| 自由入力ゆえに詰まる | 3段階ヒント＋エラーレスポンス自体を丁寧な教材にする（400 に修正方法を書く） |
| モバイルで3ペインが窮屈 | タブ切り替えUI。リクエストビルダーはフォーム部品中心でフリック入力を最小化 |
| localStorage 破損・仕様変更 | セーブに version を持たせマイグレーション。壊れたらワールドDBのみ初期化して進捗は守る |
